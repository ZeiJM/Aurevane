# Authored World PvE encounter implementation plan

**Goal:** Let a player challenge a staff-published World NPC from its real placement and enter an ordinary one-opponent battle with durable World provenance.

**Authority:** Unified Handover §§4.2, 6.1, 7.2 and 14B–F. Current integration baseline 4042f4a. Do not publish production NPCs, story, encounter rewards, or rules in this slice.

- [x] Extend the existing World publication with an optional one-opponent challenge. NPC Design owns the World placement, greeting, challenge template and optional bounded qualification tags. A draft has no effect until World Commit. Arena and Story publications remain independent. Validate settings in the request parser and SQL, and retain compatibility with records that lack the optional fields.
- [x] Project an explicit Challenge action only for the current charted, known, published NPC within range. The browser submits the NPC identifier, World version and command ID. The service loads the published candidate and prepares the canonical PvE battle. The admission RPC rechecks owner, current stationary position, placement, publication revision, challenge config, active game state, and exact replay. Follow the same catalogue/account/character/World lock order as the realm guardian, and bind the session to the server-owned target before appending version-one startup events.
- [x] Store private battle provenance keyed by session and exact character/command. Pin the published NPC ID and revision, admitted World position, target combatant ID, template, eligibility tags and database admission time. Keep the public battle view limited to existing participant presentation and a typed World origin for appropriate completion/return controls. Hall practice, PvP, guided training and the sealed realm do not enter this provenance table.
- [x] Verify through the real command and persistence boundaries. An isolated fixture must save/commit World-only NPCs, deny greeting-only, distant, stale or unowned requests, admit one duel, load it through the canonical battle reader, and replay only the exact request. Verify no event progress is awarded and no new admission depends on a retired placement. Confirm that ordinary Arena behavior and Hall completion controls still work in their adjacent tests.

For subsequent event work, read immutable `battle_events` and versioned snapshots. `damage_applied` carries target/source and HP before/after, and `battle_completed` supplies winning team or draw. The same terminal commit can carry `ai_combatant_surrendered` or `pvp_combatant_surrendered`, which set HP to zero, so neither zero HP nor the terminal event alone authorizes a genuine defeat. Exclude abandonment, administrative no contest and terminal timeout under the pinned challenge policy. A future private `opponent-defeated` receipt should retain `event_id`, battle version, bound opponent ID and committed clock, unique by session and opponent. A terminal outcome receipt is unique by session. Startup events need the same evidence path as ordinary turns.

Brown can consume only eligible wolf receipts earned during an owned attempt at the pinned farm scope, then atomically complete, grant entitlement and start the configured repeat clock on explicit return. Chicken Avenger needs an independent configured game-day bucket, one unresolved challenge per character and rule, real Avenger admission, expiry, and first/repeat reward policy. Mentor needs a bound challenge and mutually exclusive typed terminal outcomes, with a separate fast-victory bonus measured from server clocks. These consumers should not borrow Battle Hall practice, visual wildlife, PvP, or personal-realm receipts.

The local full-chain database fixture admitted a published World-only opponent, replayed after retirement, committed an engine victory and rejected a direct Mastery claim. The World command tests covered replay dispatch, and rendered result tests covered NPC, realm and Hall origins. Native authenticated browser coverage and any event defeat consumer are follow-up work.
