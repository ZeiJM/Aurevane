# Seal Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement the approved plan task by task.

**Goal:** Add configurable Seal for discipline Attack/Recovery/Utility skills without restricting other sources.
**Architecture:** Reuse ordinary status application tuning, capture and lifecycle; share a pure source/category restriction predicate between canonical and retained native legality.
**Tech Stack:** Existing TypeScript, React, Vitest and PostgreSQL migrations.
**Spec:** docs/superpowers/specs/2026-11-04-seal-design.md

## Global Constraints

- Separate branch/PR from #1011, preserve current main and historical captures.
- Categories: attack/recovery/utility, any nonempty distinct subset; Turns 1–99, default 2.
- Exempt Essence, Resonance, Support, Severance/Ascension and non-discipline actions.
- Pending effects do not block; already committed effects continue; rejection never spends costs.
- Keep Git deployments disabled; no hosted data/publication changes.

## Review Focus

- Canonical recovery/utility can contain damage: classify the behavior rather than guess from effects.
- Materialized Support/equipment actions can have legacy discipline sourceType: use canonical participant identity.
- Stacked/copied/pending Seal must preserve categories and source privacy across reload.
- A selected manual modifier must not bypass Seal; an already ongoing modifier must continue.
- AI and playable previews must use the same rejection as server commit.
