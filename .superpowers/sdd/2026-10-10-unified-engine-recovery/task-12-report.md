## Lifecycle and lock-order audit

The original claim RPC locked reservation then run. Operations read the run without locking before calling the transition, while transition/recovery/contribution/reservation paths already used the run lock. The repair takes the run lock before the claim reservation and locks the operation's run read. The existing inner re-read, CAS, idempotency and immutable execution receipt remain intact. Successful same-key replay and new-key claim dedupe still return completed outcomes after emergency stop; they do not grant XP again.

The new fresh-execution eligibility check requires production ended/archived state, an original completion timestamp, and no cancellation/emergency timestamp. This closes the archived-state loophole without deleting reservations or receipts. Emergency-first prevents an unexecuted reservation from awarding. Claim-first preserves its completed award when emergency stop subsequently wins the run lock. Whole-transaction rollback restores run/transition/reservation/claim/XP/idempotency state; the native gate additionally compares operations audits and all character facts.

Outer callers were traced: `recover_due_event_runs_v1` locks candidate runs with `FOR UPDATE SKIP LOCKED`, then delegates phase/transition work; phase recovery also locks run before phase. It does not select/lock claim reservations or call the claim executor. Existing `record_event_contribution_v1` and `reserve_event_reward_claim_v1` lock the run first. Repository app/worker source has no reward claim/reservation/contribution caller; exposed execution remains the service-only RPC, with direct calls in native fixtures. `apps/worker/src/runtime.ts` only reports ready and handles shutdown. There is no hidden bulk/cron reservation-first caller to relabel as a production executor.

Task 9 no-contest mechanics are unchanged: no Event path was added that joins or settles a battle, and unsupported encounter effects are blocked before production publication/scheduling.
